# Система мониторинга криптовалютных операций с применением ИИ

[![CI](https://github.com/Abuka/crypto-monitoring/actions/workflows/ci.yml/badge.svg)](https://github.com/Abuka/crypto-monitoring/actions/workflows/ci.yml)

Платформа для отслеживания подозрительных операций с криптовалютой. Помогает аналитику
быстро отвечать на вопросы: какие операции требуют внимания, какие кошельки ведут себя
подозрительно, какие транзакции стоит проверить в первую очередь.

Первая версия работает с блокчейном **Ethereum** (данные через Etherscan API).

## Принцип проекта

Сначала строится платформа мониторинга, затем добавляется искусственный интеллект.
ИИ — один из инструментов внутри системы, а не её единственная ценность.

```
Получение данных (Ethereum)
      ↓
   База данных
      ↓
 Расчёт риска (Rule Engine)
      ↓
   Оповещения (Alerts)
      ↓
 Интерфейс аналитика
      ↓
 Модуль ИИ (AI Engine)  ← добавляется на втором этапе
```

## Стек технологий

- **Python** — анализ данных и реализация моделей
- **scikit-learn** — машинное обучение на старте (возможен переход на PyTorch)
- **pandas** — обработка данных
- **PostgreSQL** — база данных
- **Etherscan API** — получение транзакций Ethereum (через слой-адаптер, заменяемый на свой RPC-узел)
- **Elliptic Dataset** — размеченный датасет для обучения модели

### Сбор данных и расчёт риска (CLI)

```bash
python -m collector --address 0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045 --max 15
python -m collector --block 19000000           # один конкретный блок
python -m collector --follow                   # слежение: постоянно тянуть свежие блоки (Ctrl+C — стоп)
python -m collector --score-risk               # расчёт риска + генерация алертов
python -m collector --seed-labels              # применить метки адресов (data/labels_seed.json)
python -m collector --compute-features          # числовые признаки кошельков для ML (wallet_features)
python -m collector --train-anomaly             # обучить Isolation Forest -> models/anomaly.joblib
python -m collector --score-anomaly             # применить модель: ml_score + гибридный риск
python -m collector --build-graph               # граф переводов -> граф-признаки (wallet_graph_features)
python -m collector --score-graph               # подмешать graph_score в риск кошельков
python -m collector --reset-data               # очистка данных (предпросмотр; --yes для удаления)
```

**Decision Engine.** Итоговый уровень риска определяет не формула, а решающая
логика над независимыми источниками с приоритетом
`Hard Signals → Rule Engine → Graph Analysis → AI Engine`. Ключевые инварианты:
источником считается **модуль** (несколько правил внутри Rule Engine — это один
источник); ИИ **никогда не снижает** результат правил и **в одиночку не поднимает**
уровень выше MEDIUM; Hard Signal (санкции/blacklist) → сразу CRITICAL. Все пороги
и списки — в `.env` (`DECISION_*`), не в коде. Каждое решение сопровождается
объяснением (уровень, уверенность, причины, вклад источников) — сохраняется в
`decision` (JSONB) и показывается аналитику. Подробнее — в
[docs/architecture.md](docs/architecture.md).

**ML-поиск аномалий (Isolation Forest).** `--train-anomaly` обучает модель на
признаках `wallet_features` (лог-масштаб для сумм wei + `StandardScaler`) и
сохраняет её вместе со scaler в `models/anomaly.joblib`. `--score-anomaly`
применяет модель: оценка аномальности → `ml_score` (0–100), который идёт в
Decision Engine как **подтверждающий** источник (в одиночку выше MEDIUM не
поднимает). `final_score = weight_rule·rule + weight_ml·ml` остался справочным
полем для совместимости. Если модель обучена, ML автоматически
подмешивается и в `--score-risk`, и в `--follow --score`; если модели нет — работают
только правила. Для аномальных кошельков сохраняется объяснение (топ-3 признака).
Папка `models/` — в `.gitignore` (в репозиторий кладём только код обучения).

**Graph Analysis (граф-анализ сети переводов).** Блокчейн — это граф: кошельки —
узлы, транзакции — рёбра. Модуль оценивает риск по **положению кошелька в сети
связей** — это дополняет правила (смотрят на сам кошелёк) и ML (смотрит на его
поведение). `--build-graph` строит направленный граф (NetworkX) и считает для
фокус-набора кошельков граф-метрики: in/out-степень, центральность («проходность»),
**связь с рисковыми узлами** (соседи с меткой миксер/санкции — самая важная метрика),
транзитность и веерность (массовый сбор / распыление). Метрики сворачиваются в
`graph_score` (0–100) и сохраняются в `wallet_graph_features` вместе с объяснением.
`--score-graph` подмешивает его в риск кошельков. Для Decision Engine граф —
**независимый источник наравне с ИИ**: в одиночку выше MEDIUM не поднимает, но
подтверждает другие сигналы (правило + граф → HIGH; ИИ + граф → HIGH). Веса и
нормировки — в `.env` (`GRAPH_*`). Если граф не посчитан, система работает как
раньше — `graph_score` остаётся NULL и в решении не участвует.

`--compute-features` считает для каждого активного кошелька (≥5 транзакций,
порог настраивается `--min-tx`) набор поведенческих признаков (число вход/исход,
объёмы, уникальные контрагенты, разброс, частота, доля мелких операций,
транзитность) и сохраняет в таблицу `wallet_features`. Это вход для ML-модели
поиска аномалий (Isolation Forest) на следующем этапе; сама модель пока не
обучается.

Метки адресов (`--seed-labels`) — основа атрибуции: миксеры (Tornado Cash),
биржи, санкционные адреса (OFAC SDN). Оживляют правила «Связь с миксером» и
«Санкционный адрес», а биржи исключают из частотных правил (меньше шума).
Тип метки и её источник хранятся раздельно: mixer — технический факт,
sanctioned — регуляторный статус.

Режим `--follow` опрашивает вершину цепочки и подтягивает новые блоки, сохраняя
курсор в `.collector_state.json` (после перезапуска продолжает с того же места).
Подробнее — в [COMMANDS.md](COMMANDS.md).

Полная шпаргалка команд — в [COMMANDS.md](COMMANDS.md).

### LLM-объяснения алертов (опционально)

В деталях алерта есть кнопка **«Почему это подозрительно?»** — языковая модель
пересказывает решение системы человеческим языком: резюме, причины с пояснением,
что каждая означает на практике, и на что обратить внимание при проверке.

**Роль модели ограничена жёстко и намеренно:**

> LLM **не принимает решение**, **не влияет на уровень риска** и **не добавляет
> фактов**, которых нет во входных данных.

Уровень определяет Decision Engine — детерминированная объяснимая логика. Модель
получает уже принятое решение и переформулирует его. Выключение функции не меняет
ни одной оценки риска. В промпте явно запрещено домысливать тип преступления,
называть отсутствующие в данных схемы, делать выводы о владельце адреса и
оспаривать уровень риска. В интерфейсе текст помечен как сгенерированный моделью.

Результат кэшируется на связку (алерт, язык, **версия решения**): повторный
просмотр в LLM не ходит, а при изменении решения объяснение генерируется заново.
Есть переключение языка (RU/KK/EN) и кнопка перегенерации.

#### Выбор провайдера

Провайдер настраивается в `.env`, а не в коде. Промпт, ограничения роли модели,
кэш и обработка ошибок **общие для всех вариантов** — различается только клиент,
поэтому переключение провайдера не меняет ни поведение системы, ни гарантии.

| Провайдер | Стоимость | Когда выбирать |
|---|---|---|
| `anthropic` | платный | лучшее качество формулировок |
| `gemini` | **бесплатный тариф** AI Studio | демонстрация без затрат |
| `ollama` | бесплатно, локально | нет интернета / данные не должны уходить наружу |

**Вариант 1 — Anthropic Claude.** Ключ: <https://console.anthropic.com/settings/keys>

```dotenv
LLM_PROVIDER=anthropic
ANTHROPIC_API_KEY=sk-ant-...
# LLM_MODEL=claude-opus-5   # по умолчанию
```

**Вариант 2 — Google Gemini (бесплатно).** Ключ: <https://aistudio.google.com/apikey>
— выдаётся без карты, действуют суточные лимиты.

```dotenv
LLM_PROVIDER=gemini
GEMINI_API_KEY=...
LLM_MODEL=gemini-2.5-flash   # актуальный список моделей — в AI Studio
```

**Вариант 3 — локальная модель через Ollama (без интернета и без ключа).**
Установить <https://ollama.com>, затем:

```bash
ollama pull llama3.1     # или qwen2.5, mistral — любая скачанная модель
ollama serve
```

```dotenv
LLM_PROVIDER=ollama
OLLAMA_BASE_URL=http://localhost:11434/v1   # OpenAI-совместимый эндпоинт
LLM_MODEL=llama3.1
LLM_TIMEOUT_SECONDS=120                     # локальным моделям нужно больше времени
```

Если выбранный провайдер не настроен или недоступен — эндпоинт отвечает **503** с
понятным сообщением (какую именно переменную задать, запущена ли Ollama), а
система продолжает работать без объяснений. Эндпоинт —
`POST /api/alerts/{id}/explain/`, см. [docs/api.md](docs/api.md).

### Алерты на сущность, а не на транзакцию

Одна находка должна давать один сигнал. Раньше скрининг санкционного адреса
порождал 300 CRITICAL — по одному на каждую транзакцию; формально каждый верен, но
для аналитика это шум. Как и в реальных AML-платформах, алерт теперь заводится на
**связку (кошелёк, причина)**, а транзакции хранятся как **доказательства**.

- Повторное событие с той же причиной не создаёт сигнал, а дописывается в
  доказательства: растут счётчик, период и объём; уровень при необходимости
  повышается.
- Разные причины по одному кошельку — разные алерты (санкции и дробление не
  сливаются).
- Закрытый алерт новое событие не воскрешает — заводится новый, как и раньше.

В списке видно число транзакций-доказательств, в деталях — сводка (период, объём,
счётчик) и последние 20 транзакций; остальные — через
`GET /api/alerts/{id}/evidence/`.

Схлопнуть уже накопленные алерты: `python db/migrate_alerts_to_entities.py`
(предпросмотр) и `--apply`. На текущих данных: **1214 → 685** активных алертов,
санкционный кейс — один CRITICAL с 300 доказательствами.

### Скрининг адреса по запросу

Ключевое отличие от остальных экранов: остальные **показывают** то, что уже есть в
базе, а скрининг **добывает** данные — можно назвать любой Ethereum-адрес, которого
в базе нет вообще.

Раздел «Проверка адреса»: вводишь адрес → система идёт в Etherscan, подтягивает
историю (до `SCREEN_MAX_TX`), считает признаки, ML-аномалию и граф-метрики, затем
прогоняет через Decision Engine и показывает вердикт с объяснением: уровень риска и
уверенность, метка адреса с источником, причины человеческим языком, вклад каждого
источника (Hard Signal / Правила / ИИ / Граф) и агрегаты активности. Есть переходы
«Показать связи» (граф) и «Открыть кошелёк», плюс список недавних проверок.

Запрос идёт **несколько секунд** (сеть), поэтому интерфейс показывает этапы
проверки. Результат кэшируется на `SCREEN_CACHE_MINUTES`, чтобы повторная проверка
того же адреса не расходовала лимит API — замер: «холодный» адрес ~2.2 с,
повторный из кэша ~0.05 с.

Оценку выполняет **тот же** движок, что и пакетный расчёт, — вердикт скрининга
совпадает с тем, что система скажет об этом кошельке обычным путём. Эндпоинт —
`POST /api/screen/`, см. [docs/api.md](docs/api.md).

### Страница «Граф потоков»

Интерактивная визуализация связей кошелька: аналитик видит, откуда пришли и куда
ушли средства, и идёт по цепочке кликами. Работает по принципу **эго-сети** — весь
граф (66k узлов) не рисуется никогда: сервер отдаёт центр + соседей на глубину 1–2
с лимитом узлов, дальше пользователь разворачивает граф сам.

- **Вход:** раздел «Граф потоков» в меню (поле адреса + «Построить граф») либо
  кнопка **«Показать связи»** в деталях алерта и кошелька — это основной сценарий
  расследования.
- **Отрисовка:** центр крупнее и с обводкой; цвет узла — уровень риска (та же
  светофорная схема); миксер/санкции — ромб, биржа — квадрат; толщина ребра —
  объём потока, стрелка — направление перевода; подпись — сокращённый адрес.
- **Интерактив:** клик — раскрыть связи узла (догрузка в текущий вид), правый клик
  или кнопка — сделать центром, наведение — тултип, боковая панель с потоками
  и кнопкой «Открыть кошелёк». Кнопки: глубина 1/2, центрировать, сброс.
- Если соседей больше лимита — показываются самые крупные по объёму, с честной
  пометкой «показаны N из M связей».

Библиотека: `react-force-graph-2d` (canvas, без тяжёлого DOM). Она тянет за собой
d3, поэтому страница грузится **отдельным чанком** через `React.lazy` — на
остальных экранах эти ~200 кБ не скачиваются. Эндпоинт — `GET /api/graph/`,
см. [docs/api.md](docs/api.md).

### Фронтенд (React + Vite)

Интерфейс — настоящий React-проект в [frontend/](frontend/) (исходники в `frontend/src/`,

**Сборка для показа/продакшена** (Django отдаёт готовую статику, один простой запуск):

```bash
cd frontend

cd ..
python manage.py runserver   # http://localhost:8000 — отдаёт собранный SPA
```

JWT-аутентификация работает в обоих режимах одинаково.

> Шрифты (Manrope / JetBrains Mono) подключаются из Google Fonts — это единственное,
> что требует интернета. React и весь код приложения работают локально.

### Аутентификация (JWT)

Весь API закрыт: без действующего access-токена эндпоинты отдают **401**.
Токены выдаёт `djangorestframework-simplejwt`. Время жизни настраивается в `.env`
(`JWT_ACCESS_MINUTES`, по умолчанию 45; `JWT_REFRESH_DAYS`, по умолчанию 1).

Эндпоинты: `POST /api/auth/login/` (логин/пароль → access + refresh),
`POST /api/auth/refresh/` (обновить access), `GET /api/auth/me/` (текущий пользователь),
`POST /api/auth/logout/` (отзыв refresh-токена).

**Заведение аналитиков — через Django Admin** (ролей нет, используется стандартная
модель пользователя). Регистрации в интерфейсе нет — пользователей создаёт администратор:

```bash
python manage.py createsuperuser          # создать администратора (один раз)
python manage.py runserver
# открой http://localhost:8000/admin/ , войди суперпользователем,
# раздел Users → Add user → задай логин и пароль аналитику
```

**Вход в интерфейс:** открой http://localhost:8000/ — пока нет токена показывается
экран входа. После логина токены сохраняются в браузере (localStorage), все запросы
идут с `Authorization: Bearer <access>`; протухший access автоматически обновляется
через refresh, а кнопка выхода в боковом меню отзывает токен и возвращает на экран входа.

> Для продакшена задай свой `DJANGO_SECRET_KEY` в `.env` (длиной ≥ 32 байта) — на нём
> подписываются JWT. Дев-значение по умолчанию годится только для локальной разработки.

## Тесты и CI

Ручные проверки, которыми сопровождалась каждая задача, оформлены как автотесты
(pytest). **Ни один тест не ходит в интернет**: обращения к Etherscan и
LLM-провайдерам замоканы, а исходящая сеть заблокирована на уровне фикстуры —
случайно добавленный живой вызов сразу падает с понятной ошибкой. Ключи
(`ETHERSCAN_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`) для прогона **не
нужны**.

```bash
python -m pip install -r requirements-dev.txt

# Нужна только PostgreSQL: pytest-django создаёт отдельную тестовую базу
# и накатывает на неё db/schema.sql (см. tests/conftest.py).
python -m pytest                     # весь набор
python -m pytest -v                  # со списком тестов
python -m pytest tests/test_decision_engine.py   # только инварианты движка решений
python -m pytest -k "trusted or hard_signal"     # по имени
```

`DATABASE_URL` берётся из `.env`; пользователь должен иметь право `CREATE DATABASE`
(тестовая база создаётся и удаляется автоматически).

Что покрыто:

| Файл | О чём |
|---|---|
| `test_decision_engine.py` | инварианты решающей логики: Hard Signal → CRITICAL, ИИ/граф в одиночку → максимум MEDIUM, ML+граф → HIGH, несколько правил = один источник, доверенные метки |
| `test_risk_levels.py` | границы уровней по баллам и соответствие `risk_level` → уровень алерта |
| `test_alert_aggregation.py` | один кошелёк + одна причина = один алерт, доказательства не задваиваются, закрытый алерт не воскресает |
| `test_features_ml.py` | признаки на подготовленных данных, `ml_score` в 0–100, читаемость объяснений |
| `test_llm.py` | роль LLM ограничена (не меняет уровень), кэш, работа без настроенного провайдера |
| `test_api.py` | JWT на всех эндпоинтах, валидация адреса, фильтры и пагинация |
| `test_no_external_calls.py` | страховка: сеть заблокирована, внешние ключи не нужны |

CI ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) запускается на push и
pull request в `main` и гоняет два job'а параллельно: **backend** (PostgreSQL в
сервис-контейнере, применение схемы и миграций, `manage.py check`, `pytest`) и
**frontend** (`npm ci` + `npm run build`).
